The gap

Code-quality scanners answer the wrong question.

Most technical diligence checks whether the code is well-written. It rarely checks where the critical knowledge actually sits, or whether entire subsystems depend on one or two people who have no contractual reason to stay past close.

If the one person who understands a core subsystem leaves the day after you sign, what breaks, how long until anyone else can safely touch it, and what does that do to your model?

Value at risk

A subsystem only one person can safely change is value you're paying for that can resign the week after close.

Integration drag

A single bottleneck engineer can push a migration, carve-out, or roadmap back by quarters, after the price is already set.

Deal leverage

Raised and confirmed before signing, a concentration can shape a retention package or an earn-out condition instead of becoming a post-close surprise.

What we actually measure

Where code knowledge is concentrated, file by file and subsystem by subsystem.

We measure how much of each file's history one contributor holds (the evidence), then derive a tier from that share against fixed thresholds, not a subjective judgment. Where one contributor's share crosses the line, the map turns red.

Illustrative data, not a real repository. In a report, single-contributor share is measured from commit history and the tier is derived from it against fixed thresholds.

Three tiers, from fixed thresholds, not guessed.

High-confidence: 10+ commits on a file, with one contributor holding over 70% of its history (held at Watch when a single commit accounts for most of that share). Strong evidence of concentration; confirm with management who maintains it today.

Watch: 5+ commits and over 55% share. Concentration is visible but the history is shorter; ask who maintains it today.

Distributed: no single contributor holds most of this history.

Security & data handling

Your source code is copied for one scan, and the copy is deleted when the scan ends.

The deletion is recorded. The one exception: a forcibly terminated process can leave a temporary copy behind without recording it, so we check by hand after any abnormal termination. CTM is a tool we run for you, not a cloud service you sign up to: there is no customer account and no database holding your repository.

✓

How a scan works. Your repository is cloned over HTTPS onto the machine running the analysis, into a temporary directory created for that one scan. It is read there and nowhere else. When the scan ends, whether it succeeds or fails, that directory is deleted, along with the temporary directory used to assemble the report. What survives is the report we hand you, and a deletion log.

✓

What leaves that machine. The authenticated request to your repository host to fetch the code; a metadata request to that host's API; the finished report, which we deliver to you; and, if you ask for it, the deletion record. Nothing else, unless you have agreed in writing to the optional AI narrative, which is off by default.

✓

The optional AI narrative is off. With it off, no part of your repository, no commit message and no contributor identity reaches any AI service. Every number and every finding in the report is computed deterministically from your git history on the machine that ran the scan. If we ever propose enabling it, we will ask you first and in writing.

✓

Identities are pseudonymised in everything we deliver. By default, reports identify contributors as "Contributor A", "Contributor B", with no names and no email addresses on any page. (Pseudonymised, not anonymised: this reduces exposure, it does not take the data outside GDPR.)

✓

Every report says what produced it. Each report carries its own provenance: the exact version of CTM, whether that version had local modifications, the analysis settings, the timestamp, and whether AI was used. You can verify our data-handling claims from the document itself rather than taking our word for them.

✓

Deletion is evidenced. Every removal of temporary data is recorded: which scan, which class of data, whether it succeeded, and when. We can send you that record. It deliberately contains no file names, no paths and no contributor identities, so the evidence of deletion never becomes a place your information comes to rest.

✓

Credentials. You give us a read-only token scoped to the repository you want analysed, which you can revoke at any time. It is sent to your repository host as an HTTP authorisation header and is never written into the clone's configuration, a command line, a log, or any report.

What we do not claim

We would rather tell you this than have you find it out:

–

No encryption at rest. Your code is protected while it exists by the short lifetime of the copy and by the machine's own access controls, not by application-level encryption.

–

No certification. No SOC 2, no ISO 27001, no GDPR certification, and no independent penetration test.

–

Access to the tool is protected by an operator passphrase, not individual accounts or single sign-on.

–

A forcibly terminated process can leave a temporary copy behind without recording that it did. We check by hand after any abnormal termination.

–

We support github.com, gitlab.com and bitbucket.org. GitHub Enterprise Server and self-managed GitLab are not supported today.

Working with European customers. We can sign a data processing agreement under Art. 28 GDPR. Ask us for the Security & Trust Pack: it covers the data flow, retention and deletion, access control, incident response, AI egress, subprocessors, and a GDPR readiness checklist that states the open gaps as plainly as the controls.

FAQ

What people ask before their first scan.

What does Codebase Time Machine actually analyze?

Only Git commit history and metadata: authors, dates, file paths, and commit messages. Not runtime data, and not anyone who never committed code. Git shows who wrote and changed the code; who maintains it today is a question for management, and the report says so.

Do you need write access to our repo?

No. Access is read-only, through a token scoped to the repository, and you can revoke it at any time.

What happens to our code after the scan?

Your repository is copied for a single scan and the copy is deleted when the scan ends, with the deletion recorded (a forcibly terminated process is the exception; we check by hand after one). The optional AI narrative is off by default, so nothing goes to any AI service. Delivered reports pseudonymise contributor identities by default, and each report states the exact tooling and settings that produced it. We hold no certification and do not encrypt at rest. Our full Security & Trust Pack says so, along with everything else we do and do not do.

How is "risk" actually calculated?

Tiers come from fixed commit-history thresholds. For example, 10+ commits on a file with one contributor holding over 70% share is High-confidence, unless a single commit accounts for most of that share. It's not a subjective score, and it measures concentration of history, not who maintains the code today.

What does it cost?

Every engagement is quoted individually, before you grant any access, so you know exactly where you stand up front. Book a call or email us and we'll turn a quote around quickly.

How long does a scan take?

The analysis runs in minutes to a few hours, depending on repository size and depth. Depth is your call, from the most recent commits up to the repository's complete history, and the report states the exact share of the history it analysed.

What does AI do in the report?

Nothing, by default. Every number and finding is computed deterministically from Git history. An optional AI narrative exists; we enable it only if you agree in writing first.
